# Quant Validation Audit — 거짓 성과와 경계면 버그 사냥 절차

백테스트의 가장 큰 거짓말은 "과거에 잘 됐으니 미래에도 될 것"이다. 이 스킬은 그
거짓말과 컴포넌트 연결의 어긋남을 잡는 검증 절차다. 핵심은 **존재 확인이 아니라
교차 비교** — "있는가?"가 아니라 "실제로 일관되게 작동하는가?".

## 검증 우선순위

### 1. look-ahead bias 누출 (최우선)
가장 흔하고 치명적. 그 시점에 알 수 없던 정보를 쓰는 실수.
- 전략·분류기 `next/classify/propose`가 전달받은 history "이후" 데이터에 닿지 않는지.
- 백분위·EMA·상관·정규화가 **trailing window로만** 계산되는지(전체 시계열 통계 금지).
- 검증법: 데이터를 i 시점까지 자른 입력과 전체 입력의 i 시점 출력이 동일한지
  단위 테스트로 확인. 뉴스/감성의 `asOf`가 의사결정 시점 이전인지.

### 2. 거래비용 현실성
초보 백테스트가 가장 많이 죽는 곳.
- 모든 체결이 `Broker`를 거치는지(우회 경로 없는지) 코드 추적.
- US/KR 비용 구조가 맞는지(US는 매도세 없음, 환전·SEC fee), 비용 차감 후에도
  성과가 살아남는지. 잦은 거래일수록 비용이 수익을 갉아먹는다.

### 3. 과최적화 / 다중검정
- 시도한 전략·파라미터 조합 수가 기록되는지(`triesIndex`).
- **in-sample 성과로 OOS를 평가하지 않는지**(OOS를 보며 튜닝하면 그 순간 in-sample).
- 파라미터 수 대비 표본·거래 수가 충분한지.

### 4. 통합 정합성 — "양쪽 동시 읽기"
경계면 버그는 한쪽만 봐선 못 잡는다. 생산자와 소비자를 **같이** 열어 shape을 비교:

| 검증 대상 | 생산자 | 소비자 |
|----------|--------|--------|
| 국면 → 전략 | `RegimeState.membership` | strategy-pool 활성도 |
| 전략 → 메타 | `StrategyProposal` | meta `allocate` 입력 |
| 메타×적극도 → 정산 | `MetaAllocation`×`aggressiveness` | `reconcile` 입력 |
| 엔진 → 대시보드 | `BacktestRun`/`LiveSnapshot` JSON | web 리더 타입 |
| 계좌 → 정산 | `AccountState`(통화·유니버스) | `reconcile` NAV·필터 |

함정: 래핑(`{ items: [] }`) vs 배열, snake/camelCase, 즉시응답 vs 비동기 결과.
타입 캐스팅·`any`·제네릭으로 우회된 타입 안전성을 의심한다(`build` 통과 ≠ 정상 동작).

## 실행 원칙

- **점진 검증(incremental)**: 전체 완성 후 1회가 아니라 각 모듈 완성 직후 즉시.
  경계면 불일치가 후속 모듈에 전파되기 전에 잡는다.
- **결과가 좋을수록 더 의심한다**: 비현실적 샤프·MDD는 look-ahead/비용 누락의 신호.
- Grep으로 패턴을 전수 추출하고(예: 모든 체결 호출, 모든 status 업데이트), 가능하면
  자동 대조 스크립트를 만들어 재현 가능하게 한다.

## 리포트 형식

`artifacts/_qa/{module}_report.md`에 작성한다:
- **통과 / 실패 / 미검증**을 명확히 구분.
- 각 실패: `파일:라인` + 무엇이 어긋났는지 + **구체적 수정 방법**.
- 경계면 이슈는 생산자·소비자 **양쪽 에이전트 모두**에게 알린다.
- 검증에 쓴 스크립트·테스트도 남겨 재현 가능하게.
